Проект транспортная система home_node
1. Назначение проекта
Создание фоновой транспортной системы "Home Node", которая работает на компьютере пользователя и обеспечивает:
1.	собственную криптографическую идентификацию Home Node; 
2.	идентификацию удалённых Home Node; 
3.	хранение списка известных узлов; 
4.	постоянный приём входящих файлов; 
5.	передачу исходящих файлов удалённым узлам; 
6.	передачу файлов между различными Home Node, и - между Home Node и привязанным(ми) к нему смартфоном(ами); 
7.	временное хранение файлов в simple_data/; 
8.	автоматическое удаление устаревших файлов; 
9.	работу независимо от пользовательского приложения "Simple". 
Ключевой принцип:
home_node — транспортный сервер и менеджер доставки.
Simple — пользовательское Python-приложение, которое работает с файлами, но не занимается сетью, идентификацией и транспортом.
________________________________________
2. Разделение ответственности
Архитектура должна состоять из двух независимых уровней.
2.1. Home Node
Home Node отвечает за:
•	криптографическую идентичность; 
•	Node ID; 
•	известные узлы; 
•	сетевые подключения; 
•	authentication; 
•	передачу файлов; 
•	контроль срока жизни файлов; 
•	маршрутизацию; 
•	приём и отправку; 
•	работу с simple_data. 
Home Node не должен знать, существует ли вообще Simple. Он работает исключительно с каталогами и файлами.
________________________________________
2.2. Simple
Simple отдельное приложение. В будущем будет пользовательским интерфейсом.
Он сможет:
•	показывать файлы; 
•	помещать файлы в outgoing/; 
•	помещать файлы в to_phone/; 
•	забирать файлы из incoming/; 
•	забирать файлы из from_phone/; 
•	отображать состояние. 
Но Simple не должен:
•	создавать Node ID; 
•	создавать криптографические ключи; 
•	выполнять authentication; 
•	открывать TCP-сервер; 
•	управлять соединениями; 
•	знать протокол Node authentication; 
•	самостоятельно передавать файлы между node.

4. Идентичность Home Node
Каждый компьютер должен иметь собственную идентичность.
Она хранится исключительно здесь:
home_node_data/
└── home_node_key/
    ├── node_private.key
    └── node_public.key
4.1. Ключи
Используется Ed25519.
Private key: node_private.key.
Public key: node_public.key.
Размер публичного ключа — 32 байта.
Private key и public key должны проверяться на соответствие при загрузке.
________________________________________
5. Node ID
Node ID однозначно вычисляется из public key.
Длина Node ID:
32 hex characters
Node ID не хранится отдельно как источник истины.
Он всегда вычисляется из public key.
Следовательно:
два разных public key → два разных Node ID.
И:
один public key → один и тот же Node ID.
________________________________________
6. known_nodes.json
Список Home Node, известных серверу, находится здесь: home_node_data/node_data/known_nodes.json
Пример логической записи:
{
  "node_id": "...",
  "host": "192.168.1.162",
  "port": 8766
}
Минимальная информация:
•	Node ID; 
•	IP/hostname; 
•	TCP port. 
В дальнейшем могут быть добавлены:
•	public key; 
•	имя узла; 
•	last_seen; 
•	статус; 
•	другие параметры. 
________________________________________
7. Известные узлы
В тестах участвуют два компьютера: Node A, и Node B.
Каждый Home Node имеет собственный known_nodes.json.
Собственный Node ID в качестве удалённого узла добавлять не нужно.
________________________________________
8. Network server
Home Node transport server находится: home_node/server_node.py
________________________________________
9. Постоянный TCP-сервер
Home Node постоянно слушает входящие TCP-соединения.
Например:
0.0.0.0:8766
Порт конфигурируется.
При запуске сервер:
1.	загружает собственную идентичность; 
2.	загружает known_nodes.json; 
3.	создаёт необходимые каталоги simple_data; 
4.	запускает TCP listener; 
5.	запускает фоновые задачи; 
6.	начинает принимать соединения. 
________________________________________
10. Обработка входящего соединения
Для каждого входящего TCP connection создаётся независимая asynchronous task.
Логика:
TCP connection
      ↓
Node Authentication
      ↓
проверка удалённого Node ID
      ↓
проверка public key
      ↓
проверка signature
      ↓
authenticated connection
      ↓
приём transfer message
      ↓
приём файла
      ↓
проверка целостности
      ↓
simple_data/incoming/
Один клиент не должен блокировать остальных.
Например одновременно:
A → B
C → B
B → A
должны обрабатываться независимо.
________________________________________
11. Authentication
Authentication является частью транспортного уровня.
Она должна подтверждать:
1.	удалённый узел действительно владеет соответствующим private key; 
2.	его public key соответствует заявленному Node ID; 
3.	signature корректна; 
4.	соединение адресовано правильному Node. 
Для этого используются:
node_auth.py
node_auth_network.py
________________________________________
12. Authentication protocol
При установлении соединения:
A → B
B создаёт challenge.
A формирует authentication response:
node_id
public_key
signature
Signature вычисляется по однозначно определённому authentication payload.
Payload должен включать как минимум:
challenge
sender_node_id
receiver_node_id
После этого принимающая сторона:
1.	проверяет Node ID; 
2.	проверяет соответствие Node ID/public key; 
3.	создаёт Ed25519 public key; 
4.	проверяет signature; 
5.	только после этого разрешает передачу файла. 
________________________________________
13. Transfer protocol
После успешной authentication начинается отдельный file-transfer protocol.
Authentication и file transfer должны быть логически разделены:
Authentication
        ↓
Authenticated connection
        ↓
Transfer protocol
Нельзя считать TCP connection authenticated только потому, что TCP connection установлен.
________________________________________
14. Framing
Для TCP используется framing.py
TCP является byte stream, поэтому каждое сообщение должно иметь frame boundary.
Все protocol messages должны передаваться через единый framing mechanism.
________________________________________
15. Transfer message
Перед передачей файла отправляется metadata.
Она должна позволять получателю определить:
•	transfer ID; 
•	имя файла; 
•	размер; 
•	hash; 
•	отправителя; 
•	получателя; 
•	тип передачи. 
Минимально:
transfer_id
filename
size
sha256
sender_node_id
receiver_node_id
________________________________________
16. Transfer ID
Каждая передача получает уникальный:
transfer_id
Он используется для:
•	диагностики; 
•	логирования; 
•	различения нескольких файлов; 
•	контроля повторной передачи; 
•	дальнейшего расширения протокола. 
________________________________________
17. Входящие файлы
После успешной передачи Node → Node файл помещается в simple_data/incoming/.
Впоследствии Simple сможет его забрать. Home Node не должен требовать запуска Simple.
________________________________________
18. from_phone
В будущем передачи phone → Home Node должны попадать в simple_data/from_phone/.
В архитектуре для телефона должен быть отдельный destination.
________________________________________
19. from_pc
Папка simple_data/from_pc/ не обрабатывается transport server.
Файлы здесь появляются в результате работы Simple. Home Node их не отправляет автоматически.
________________________________________
20. Исходящие файлы
Для Node → Node передачи используется simple_data/outgoing/
Если в этой папке появляется файл, сервер рассматривает его как задачу: "отправить известным Home Node".
________________________________________
21. Передача outgoing
На текущем этапе действует правило, что файл из simple_data/outgoing/ отправляется всем подходящим известным Home Node.
В будущем предполагается наличие параллельной точной маршрутизации "outgoing/<node_id>/" для доставки файлов на конкретный Home Node.
________________________________________
22. to_phone
Папка simple_data/to_phone/ зарезервирована для Home Node → smartphone.
После реализации связи со смартфоном нужно будет добавить обработку этой папки.
Однако серверная архитектура должна быть построена так, чтобы добавление этого направления не потребовало второго Home Node сервера.
________________________________________
23. Один сервер, несколько направлений
Используется один основной: server_node.py.
Внутри него могут существовать отдельные asynchronous handlers:
incoming node connection
outgoing node worker
phone connection
file expiration worker
Таким образом:
                Home Node Server
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   Node incoming   Node outgoing   Phone
________________________________________
24. Фоновый outgoing worker
Сервер должен периодически проверять:
simple_data/outgoing/
simple_data/to_phone/
Предположительный интервал - 5 минут.
Но сам механизм должен быть параметром конфигурации.
________________________________________
25. Retry
Если удалённый Node недоступен:
file appears
    ↓
attempt
    ↓
failed
    ↓
wait
    ↓
retry
В течение TTL файла.
Например:
TTL = 5 minutes
retry interval = 30 seconds
Получается несколько попыток:
00:00
00:30
01:00
01:30
...
04:30
Точные значения должны быть конфигурационными.
________________________________________
26. TTL файлов
Каждый файл в очередях:
outgoing/
to_phone/
имеет ограниченное время жизни.
Начальное требование: TTL = 5 минут. После TTL файл считается устаревшим.
Но сервер должен отличать:
старый файл
от:
нового файла, появившегося позже
________________________________________
27. Безопасность
Private key никогда:
•	не передаётся по сети; 
•	не попадает в JSON; 
•	не выводится в обычный лог; 
•	не копируется между компьютерами. 
Каждый физический Home Node должен сам создать собственную identity.
________________________________________
28. Очень важное правило развёртывания
Компьютер A и компьютер B никогда не должны использовать один каталог ключей.
Нельзя копировать A/home_node_data/home_node_key/ на B/home_node_data/home_node_key/
Каждый компьютер выполняет NodeIdentity() самостоятельно.
После создания:
NodeID_A != NodeID_B
Это обязательное условие.
________________________________________
29. known_nodes.json и ключи
known_nodes.json не должен содержать private key.
В зависимости от выбранного security model он может содержать public key удалённого узла.
Рекомендуемый вариант:
{
  "nodes": [
    {
      "node_id": "...",
      "host": "192.168.1.162",
      "port": 8766,
      "public_key": "..."
    }
  ]
}
Тогда сервер сможет проверять не только:
NodeID ↔ public key
но и:
полученный public key == сохранённый public key
Это защищает от ситуации, когда кто-либо предъявляет новый ключ с тем же вручную указанным Node ID.
